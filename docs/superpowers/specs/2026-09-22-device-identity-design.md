# 设备身份模型设计：逻辑名退役、物理成员成行

- 日期：2026-09-22
- 状态：待评审
- 后续：评审通过后编写实施计划（writing-plans）

## 一、背景与问题

现状 `devices` 表以"逻辑设备"为行：一台堆叠（Aruba VSF / Cisco 堆叠）占一行，成员序列号等以逗号串存储。物理身份在**四处展示层各自展开**、格式已经分叉：

| 位置 | 现状 |
|---|---|
| 仪表盘设备清单 | 前端 `memberSuffixes` 展开，`名字-1`（真实号不补零） |
| 软件版本报告 | 后端 `reports.py::_expand_device_members`，`名字-1` |
| 多设备拓扑图 | 后端 `topology.py::_expand_physical_devices`，**回退号 `-01`（固定两位）** |
| 端口连接图 | 前端 `PortTopologyCanvas` 自拼内部 ID `-M1`，显示 `(Member 1)` |
| 保修（生命周期卡片） | **只有序列号，没有物理名** |

问题：

1. "逻辑名"被当作"设备"展示，认知混乱（用户明确反馈）；
2. 物理成员不是一等公民——查"某台物理交换机"要展开、要 join、格式还不一致；
3. 同一拼名规则 4 处重复维护，已出现格式分叉（与 cerebrum 记录的"同一规则多处维护必分叉"教训一致）。

目标：

- **位置身份与硬件身份分层**：名字 + IP 是"工位"（连接与配置的对象），序列号是"硬件"（保修与盘点的对象）；
- **物理成员成行**：物理设备在库中是一行，所有物理视图零展开；
- **格式单一来源**：`名字-编号` 全站唯一；
- 硬件变更（成员增/减/换、整机换代）可检测、可留痕、可追溯。

## 二、核心概念与术语

| 概念 | 定义 | 载体 |
|---|---|---|
| 位置身份 | 网络中的"工位"：设备名 + 管理 IP。运维脚本、监控、文档的锚点，硬件更换不变 | `kind='stack'` / `'standalone'` 行 |
| 硬件身份 | 可搬动、可保修、可报废的实体机器 | 序列号（`kind='member'` 行 / 档案表） |
| 硬件指纹 | `(platform, 型号集合, 序列号集合, 成员数)`，每次成功采集计算 | 变更检测的输入 |
| 变更事件 | 指纹 diff 的结果记录（成员增/减/换/重排、整机更换、形态变化） | `device_change_events` 表 |
| 调拨 | 同一序列号在两个位置间移动（由档案表 `last_device` 变化检出） | 变更事件 + 档案表 |
| 时代分界 | "疑似整机更换"事件的记录点，趋势/历史按它分代 | 变更事件 |
| 备件 / 报废 | 机器离开网络后的**意图**（系统不猜，人工标注） | 档案表 `status` 列 |

**kind 语义**（`devices.kind`）：

- `stack`：有堆叠/VSF 配置的管理体（**哪怕当前只有 1 个成员**）。判定按**配置解析**，不按成员数。
- `standalone`：单机。既是管理体也是物理机，自身携带序列号。
- `member`：堆叠的物理成员行。只表示"当前占位"。

术语统一为 **stack / standalone / member**（代码、DB、UI 一致）；"逻辑名"一词退役，界面上一律称"堆叠"。用户新增设备时 kind 未知，默认 `standalone`，首次采集后修正（首次采集不触发"形态变化"事件——没有上次指纹）。

## 三、数据模型（schema v18）

> 当前 `SCHEMA_VERSION = 17`，本次迁移为 `_migrate_v18`；按项目约定同步维护 v1 CREATE TABLE 与迁移函数，并递增常量。

### 3.1 `devices` 表新增列

| 列 | 类型 | 说明 |
|---|---|---|
| `kind` | TEXT NOT NULL DEFAULT 'standalone' | `stack` / `standalone` / `member` |
| `stack_name` | TEXT DEFAULT '' | 成员行：所属堆叠名；其余为空 |
| `member_no` | INTEGER | 成员行：成员号（真实号）；其余 NULL |

约束：成员行 `UNIQUE(stack_name, member_no)`（部分唯一索引，`WHERE kind='member'`）。

成员行字段规则：

- `name`：**物化派生** = `{stack_name}-{member_no}`，堆叠改名/编号变化时同步 UPDATE；保持 `UNIQUE(name)`，所有按名查询机制（详情页路由等）对成员行同样可用（存储名恒定；1 成员堆叠的**展示**省略后缀，见第四节）；
- `serial_number`：单值（不再逗号串）；
- `model` / `version`：成员级，来自既有 member_* 逗号串的拆分结果；
- `ip`：**不存**——成员共享堆叠管理 IP，存储冗余且误导；API 返回时从堆叠行带出；
- `location`：默认继承堆叠（跨机架堆叠可后续覆盖，先不做）；
- `last_synced`：成员级最后采集时间，离线判定沿用 30 天规则。

堆叠行的 `member_*` 逗号串列：**第一阶段保留作缓存**（减少改动面），标注"第二期退役"；成员行是权威数据源。

### 3.2 `port_snapshots` 表新增列

| 列 | 类型 | 说明 |
|---|---|---|
| `member_no` | INTEGER NULL | 端口所属成员号，写入时由端口名前缀解析（复用 `topology.py::_member_slot_for_port` 的规则）；逻辑口（Po/Hu/lag）为 NULL |

历史数据回填：从 `port_name` 前缀尽力解析，失败置 NULL（不回填历史不算编造——前缀本身就是事实）。

### 3.3 `device_change_events` 表（新）

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `device_id` | 位置行（stack/standalone）的 id |
| `detected_at` | 检测时间（采集时间） |
| `kind` | `member_added` / `member_removed` / `member_replaced` / `member_reordered` / `full_replacement` / `form_change` |
| `detail` | JSON：变化前后指纹、涉及的序列号与槽位、调拨来源/去向 |
| `note` / `annotated_by` | 人工备注（可选） |

展示：设备页"硬件变更"区；可选同步一条 info 级告警走既有告警框架。

### 3.4 `device_members` 档案表：定位明确为"序列号历史层"

保留现表（SN 主键、采集时 upsert、永不删），职责：

- 记录**曾见过的每一台硬件**：`first_seen` / `last_seen` / `last_device` / `last_member`；
- 新增 `status` 列 ∈ `active`（默认）/ `spare`（备件在库）/ `retired`（报废）——**人工标注**；
- 与成员行的分工：**成员行 = 当前占位；档案表 = 历史**。换件后旧硬件在此留档，保修记录由既有 `extra_rows` 机制继续可见。

### 3.5 迁移（v18）

- 现有 36 行：按 `serial_number` 逗号判定——12 台堆叠 → `kind='stack'`，24 台单机 → `standalone`；
- 为 12 台堆叠创建 **25 个成员行**（11 台双成员 + 1 台三成员 SZXD1SWI01），拆分规则与 `reports.py::_expand_device_members` 完全一致（序列号同序 1:1）；
- 迁移后：61 行 = 12 stack + 24 standalone + 25 member；
- **幂等**：可重复运行；
- **回滚**：配置类外键语义未变（见下），停用成员行（kind 过滤反转）即可回退。

## 四、物理名格式（唯一规则）

**用户可见的物理名一律为 `{名字}-{编号}`，编号不补零。**

- 真实成员号优先，来源优先级：
  1. `member_ids`（Aruba VSF，已有解析）/ Cisco 堆叠成员表第 1 组（`collector_service.py` 成员表正则**已经解析到 Switch 号但被丢弃**，接上即可，近零成本）；
  2. 端口名前缀（`Gi2/0/x`、`2/1/x` 均直接暴露成员号，平台无关）；
  3. 顺序号兜底——**尽量避免**：跳号场景会身份漂移（3 成员堆叠拆走成员 2 后，成员 3 会被顺序号标成 `-2`，成员行"改名"，历史与保修断链）。
- 跳号原样（`-1`、`-3`，不补 `-2`）；
- 展示名规则：当前成员数 ≥2 → 物理名；**=1 → 只用基础名**（与单机一致；2→1 收缩后显示名回到基础名是有意为之）；
- 单机（standalone）不加后缀。

**单一实现**：后端新建 `backend/utils/device_identity.py`，提供成员号解析/物理名拼装/展示名规则；`reports.py`、`topology.py`、`collector_service.py`、生命周期 API 改用之；前端保留 `memberSuffixes` 为唯一来源（如改造后零调用方则删除——cerebrum 教训：零调用方的 export 直接删）；端口连接图**用户可见**的 `(Member 1)` 改为 `-1`（内部节点 ID `-M1` 不在范围内）。

## 五、采集写入路径

每次**成功**采集后（单事务）：

1. upsert 位置行（stack/standalone，现状逻辑不变）；
2. 维护成员行：按本次指纹 upsert/新增行；消失的成员 → 行**保留 + 离线标记**（不删除；用户已在讨论中确认此语义）；堆叠行被删除时成员行级联删除；
3. 计算硬件指纹，与上次对比 → 写变更事件（见第六节）；
4. upsert `device_members` 档案（现状已有），并检出调拨（`last_device` 变化 → 事件 detail 记录来源/去向）；
5. **失败保护沿用"空/未知不覆盖"**：本次采集 serial 为空或"未知" → 不碰成员行、不写变更事件、不更新指纹。

序列号唯一占位不变量：一个 SN 同一时刻只能是一个位置的当前成员。两个堆叠采集存在时间差时可能出现同一 SN"同时在两处"——落档以最新采集为准（档案表以 SN 为主键，天然覆盖），旧位置残留的成员行标记离线并由调拨事件说明去向。

## 六、硬件变更检测

指纹 = `(platform, 型号集合, 序列号集合, 成员数)`；每次成功采集逐位置独立 diff：

| 本次 vs 上次 | 判定（事件 kind） | 处置 |
|---|---|---|
| 全同 | 无变化 | — |
| 序列号集合变大（旧 ⊆ 新） | `member_added` | 建成员行；提示 |
| 变小（新 ⊆ 旧） | `member_removed` | 成员行离线；提示 |
| 集合相同、槽位↔序列号绑定变化 | `member_reordered` | 更新绑定；提示 |
| 部分交集、同槽位换了 SN | `member_replaced` | 更新槽位占用者，旧 SN 留档案；提示（detail 注明新 SN 是否已知设备/来自何处） |
| 平台或型号族变化，或 SN 集合零交集 | `full_replacement` | 记"时代分界"；醒目提示待人工备注 |
| kind 变化（stack ↔ standalone） | `form_change` | 记录并提示（场景：整堆叠被重刷为独立设备，或反之） |

**处置两档**：

- 成员级变化（增/减/换/重排）：自动处理 + 留痕；
- 整机级变化（换代、形态）：**只记录、只提示，不做任何自动破坏动作**——采集照常、历史全留，由人备注。

**三条铁律**：

1. 序列号唯一占位不变量（见第五节）；
2. **意图不自动化**：系统只判断"什么变了"（确定性集合比较）；"为什么变、怎么处置"（备件/报废/借调）一律人工标注（档案表 `status`），绝不猜；
3. kind 判定按配置（有堆叠/VSF 配置即 `stack`），不按成员数。

典型场景（已验证全部落入上述规则，无需新增逻辑）：

- **两个 VSF 互换成员**：两个位置各报 `member_replaced`，调拨记录串联（`SN3: B→A；SN2: A→B`），人一眼看出是交换；
- **从 A 拆一台给 B**：A 报 `member_removed`、B 报 `member_added`，调拨 `SN2: A→B`，保修随 SN 走；
- **拆一台入库、原 VSF 变单机**：报 `member_removed`；留下的是 1 成员堆叠（配置未重刷）或 `form_change` 成单机（配置已重刷）；入库那台需人工标注为 `spare`，否则 30 天后会混进"离线异常"。

## 八、工程纪律

1. **DAL 收敛**：devices 查询收敛到 `device_dal` 的 `list_managed()` / `list_physical()` 两个入口；约定**禁止新代码裸查 `devices`**（现状约 20 处查询点，实施第一步用 GitNexus impact 汇总 `FROM devices` 清单逐一处理）；

3. **回滚安全**：配置类外键（collections / port_snapshots / alerts / audit_*）语义未变——仍指向位置行；停用成员行即可退。

> 说明：`collections` 等表的外键**语义不变**是本方案与"物理行即设备"全量重构的关键区别——不需要"-1 是主成员"的隐藏约定。

## 十二、决策记录（本设计讨论中的取舍）

| 曾考虑的方案 | 结论 | 原因 |
|---|---|---|
| 只加"是否堆叠"布尔列 | 否 | 冗余派生数据（序列号串已表达），且不解决物理成员可见性；"是否堆叠"的单一来源应是一个代码 helper |
| 物理行即设备（全量重构） | 否 | 配置/SSH/审计天生是堆叠级；会导致"-1 是主成员"隐藏约定 + 采集/Ping 去重 + 全表外键语义迁移，HIGH 风险 |
| 只升格档案表、不建行 | 否（降为备选） | 用户可见效果接近，但库中"物理设备"仍非一等公民，join 逻辑多处重复 |
| **kind + 成员行（本方案）** | **采纳** | 配置类外键语义不变、无主成员约定；物理设备真正成行；格式与检测各有单一来源 |
| 成员消失即删除行 | 否 | 用户确认：保留 + 离线标记，历史连续；删除仅发生于堆叠行被删时（级联） |
| 顺序号作为成员号 | 否 | 跳号会身份漂移（历史/保修断链）；仅作最后兜底 |

## 十三、附加需求：设备生命周期（EoS/EoL + 维保）的显示、编辑与状态标识（2026-09-22 追加）

**现状（已具备）**：

- 数据层：`eol_models`（型号级 EoS/EoL）+ `device_lifecycle`（逐序列号维保）+ Cisco EoX 自动刷新（`eox_client`，凭据到位时）；
- API：单设备读写、批量粘贴导入、型号手工登记、概况（`/api/lifecycle/*`）；
- 审计侧：判定器已有（`eol_announced` / `warranty_expired` / 未登记），走合规审计报告；
- 界面：仅设备详情页的 `LifecycleCard`（显示 + 编辑）。

**缺口**：① 全局入口（一级导航页）；② 状态标识（本期为三色标识；告警推送后续可选）。

**需求**：

1. **入口（新增「生命周期」导航页）**：列出全部**物理设备**（member + standalone，物理名 + 序列号），列：型号、停止销售、停止支持、维保到期、状态（正常/即将到期/已过期/未登记）、来源（自动/手工）、最后核验；支持筛选（状态/位置/型号）与排序；编辑能力：逐行改维保日期、型号 EoL 手工登记、批量粘贴导入（复用既有 API）。
2. **颜色标识（本期不做邮件/推送）**：维保状态用三色标识，判定顺序如下——
   - **绿色 = 在保**：有到期日，剩余 > 2 个月；
   - **橙色 = 临近出保**：有到期日，剩余 ≤ 2 个月；
   - **橙色 = 未登记**：未填写到期日；
   - **红色 = 已出保**：有到期日且已过期；或未填写到期日、但备注（`note`）为 `Unavailable`（从 Cisco / HPE 保修查询页抄录时，查询无结果即填它 → 按出保处理）。
   匹配口径：备注去首尾空格、忽略大小写后**等于** `unavailable`。
   应用位置：① 生命周期页每行状态列；② 设备详情页 `LifecycleCard` 的维保行。颜色与既有语义色板对齐（成功 / 警告 / 错误），不引入新色；两处共用同一套判定 helper，保证显示一致。
   **EoS/EoL 配色（同一三色原则，阈值 6 个月）**：对「停止销售」与「停止支持」两个日期**分别判定、取最严重者（红 > 橙 > 绿）**作为型号状态色——已过 = 红；剩余 ≤ 6 个月 = 橙；剩余 > 6 个月 = 绿；两个日期都未登记 = 不着色（灰，列入"未登记"筛选）。
3. **与审计的分工**：审计 = 合规评审（周期性、入报告）；生命周期状态 = 界面颜色标识（本期）；告警系统接入（告警页 + 邮件、EoS/EoL 按型号折叠）列为**后续可选**——同一数据源、两个出口。
4. **与身份模型的关系**：维保逐序列号 → 天然落在成员行 / 档案表；EoL 按型号 → 型号到物理设备映射。成员行落地后，保修卡与生命周期页可直接显示物理名（补上当前唯一缺口）。**建议在第一步之后接入**（或独立排期，两者互不阻塞）。
5. **与现有入口的关系（2026-09-22 定案）**：设备详情页 `LifecycleCard` 的编辑能力**保留**（看某台设备时就地修正单台；含 EoX 刷新与型号 EoL 登记）；新页面承担全局视角与批量导入。两处共用同一 API、同一保证期数据、同一颜色判定 helper——不存在双写不一致。
