# AI 专家简报（二期收官）—— 设计与实施计划

> 上游：`docs/superpowers/plans/2026-09-18-compliance-audit.md`（总计划："判定一律由确定性规则引擎做，
> AI 只负责讲成人话（二期，复用日志分析的 LLM 配置与脱敏）"）
> 本文件 = 设计稿 + 实施计划（本项目惯例）。

## 一、边界（最重要的一条）

**判定归引擎，叙事归 AI**。简报的 prompt 明确约束：

> 只能根据给定的建议条目组织语言；**不得新增任何未列出的问题、命令或日期**。

理由：AI 一旦"自由发挥"，就会编出引擎没发现的问题 —— 那正是"资深专家评审"这台机器的可信度所在
（净 std 移植时定下的"零幻觉"原则）。简报里也不出现"评分/合规率"字样（审计是建议，不是打分）。

## 二、两份简报（用户定案：都做）

| | 单台简报 | 全网简报 |
|---|---|---|
| 落点 | 查看器审计面板「生成专家简报」 | 配置审计页「生成简报」 |
| 输入 | 该设备的**确定性结果**：设备上下文（位置/平台/型号/生命周期）+ 统计 + findings 摘要（档位/标题/规则 id/建议/依据）+ 已批准例外 | 最新一次运行的**聚合**：总数/按档位/按来源/收敛恶化榜/折叠的集体性条目/生命周期待查台数 + 按规则命中设备数 Top N |
| 输出 | 一页 Markdown：整体印象 / 最该先做的 2–3 件 / 配套关系 / 时效风险 / 例外说明 | 几段话（管理层视角）：整体态势 / 本周变化 / 建议关注的三件事 / 数据可信度说明 |
| 存储 | **不落库**（讲解随时可重新生成；落库还要处理过期与指纹绑定） | 同左 |

**不喂配置原文**（省 token，也减少敏感面）；但 findings 的现状/证据文本**必须先打码**
（`snmp-server community XXX` 之类会带出凭据值——项目纪律：凭据值不外发）。

## 三、实现要点

**1. 凭据打码 `backend/utils/redact.py`（新增，独立可测）**

行级替换（保留命令、打掉值）：`snmp-server community X` / `password|secret|key|key-string X` /
Cisco `$9$…` / `$5$…` 哈希 / `aaa … key X` / `ciphertext` 等 → `<REDACTED>`。
简报发送前对 `current` / `evidence.text` / `fix` 统一过一遍。

**2. 简报服务 `backend/services/audit_briefing.py`（新增）**

- 复用 `services/log_analyzer` 的 **provider 降级链**（`_load_providers` / `_call_one_provider`；
  私有函数跨模块引用是权宜——重构 LLM 管道超出本任务范围）
- `build_device_briefing(env) -> prompt` / `build_network_briefing(data) -> prompt`（纯函数，可单测）
- `generate_device_briefing(...)` / `generate_network_briefing(...)`：调用 → 失败时抛可读异常
- 无 key / 全部 provider 失败 → **可读原因**（简报是加分项，绝不影响审计本身）

**3. API（`backend/api/audit.py` 增两个端点）**

| 端点 | 说明 |
|---|---|
| `POST /api/audit/device/{name}/briefing` | 单台简报（即时算，不落库） |
| `POST /api/audit/briefing?run_id=` | 全网简报；缺省用最新一次 done 运行 |

**4. 前端**

- 查看器审计面板：标题栏加「生成专家简报」按钮 → 对话框（Markdown 渲染为纯文本分块 + 复制按钮）
- 配置审计页：头部加「生成简报」按钮 → 同款对话框
- i18n zh/en；简报正文不入 i18n（规则与结论本就是中文，与"规则正文不入 i18n"同一原则）

## 四、实施步骤（每步单独提交）

1. 本计划文档
2. `utils/redact.py` + 测试（凭据打码是纪律问题，先做且独立可测）
3. `services/audit_briefing.py`（prompt 构建纯函数 + 调用链复用 + 降级）+ 测试（mock LLM）
4. 两个 API 端点 + 测试
5. 前端两个入口 + i18n + 构建
6. 浏览器端到端（有 DeepSeek key 可实跑一次真简报）+ `.wolf` 记录

## 五、验证方式

- 单测：打码（各类凭据形态 + 不误伤普通配置行）；prompt 构建（含统计/榜/例外/生命周期；不含配置原文）；
  mock LLM 返回 → 简报生成；无 provider → 可读错误
- 端到端：真实调用一次 DeepSeek（配置里有 key），确认简报**只**引用给定条目、无新造问题
- 回归：443 项全绿（本项不动判定链路，等价性基线不受影响）

## 六、风险与坑

1. **幻觉是最大风险**：prompt 必须硬约束"只组织给到的内容"；简报正文里明示"内容来自规则引擎"。
2. **敏感值外发**：`redact_secrets` 要在**所有**发送路径上（单台/全网）都过一遍；测试覆盖类型 5/7/9 哈希与团体字。
3. **成本**：单台一次调用（prompt 几百 token）；不做"一键全网 36 台"（会贵，且用户没要）。
4. **失败必须不阻塞**：审计结果页面/接口在 LLM 不可用时一切照旧。
