# 审计趋势与历史（二期）—— 设计与实施计划

> 上游：`docs/superpowers/plans/2026-09-18-compliance-audit.md`（配置审计总计划）
> 前置：`docs/superpowers/plans/2026-09-20-exceptions-registry.md`（例外机制，已落地）
> 本文件 = 设计稿 + 实施计划（沿用本项目做法，二者合一）。

## 一、背景与目标

审计结果已于每次全网审计入库（`audit_runs` / `audit_findings`，v13 起），
但**前端一处都没消费**：`auditApi.runs/runDetail` 定义了没人调，全网审计按钮没有宿主页面。
本项补齐「审计结果」的主页，回答三个问题：

1. **现在怎么样** —— 最新一次审计的统计（建议数 / 已批准例外数 / 指纹是否变过）；
2. **在收敛还是恶化** —— 趋势曲线 + 按规则的收敛/恶化榜；
3. **历史每次什么样** —— 运行列表 + 单次明细下钻（含豁免标注）。

### 用户定案（2026-09-20）

| # | 决策 | 定案 |
|---|---|---|
| 1 | 页面位置 | **新建独立页「配置审计」**（导航加一项）；标准（规则/例外）与结果（趋势/历史）分开 |
| 2 | 触发方式 | **采集后自动跑一次 + 手工触发**；页面上放显眼的「全网审计」按钮 |
| 3 | 图表粒度 | **每周只取该周最后一次运行**画图（与"配置按周存、流量周锚定"的既有惯例一致）；**本周尚无运行时不画本周点**（避免把上周数据画成本周） |
| 4 | 榜与图同基准 | 收敛/恶化榜对比 = 最新周最后一条 vs 上一周最后一条（避免"榜变了但图没动"） |
| 5 | 头部统计 | 显示**最新一次**运行的统计 |

## 二、设计

### 图表内容

- **趋势曲线**（recharts，沿用 Dashboard 的 `CHART_COLORS` 深色风格）：
  双线 = 建议数 / 已批准例外数；可切换按**档位**（5 线）或按**来源**（3 线）拆分；可按站点筛选。
  X 轴 = 周（每周最后一条运行）。**已批准例外不计入建议数**（与例外机制的口径一致）。
- **收敛/恶化榜**：按规则对比最新周 vs 上周的"未豁免命中设备数"delta，按 |delta| 降序。
- **历史运行列表**：全部运行（时间 / 触发方式 / 设备数 / 建议数 / 例外数 / 指纹变化标记），
  点任一条 → 明细对话框（按档位、设备筛选；豁免条目带标注）。

### 后端

**1. 提取 `run_full_audit()`（重构，行为不变）**

目前整段"全网审计并落库"逻辑写在 `api/audit.py::run_audit` 端点函数里。采集后自动跑也要用它，
所以提取到 `backend/analyzers/compliance/runner.py::run_full_audit(db, std, trigger)`，
端点改为薄包装（校验 trigger → 调用 → 返回）。**改造后 387 项测试必须全绿**。

**2. 新端点（只读）**

| 端点 | 说明 |
|---|---|
| `GET /api/audit/trends?weeks=26&site=` | 周序列：每周取最后一条 done 运行；每条含总数、已批准例外数、按档位/来源拆分、`ruleset_changed`/`exceptions_changed`（与前一个点比 hash）。本周无运行则该周不出现 |
| `GET /api/audit/trends/diff?from_run=&to_run=` | 收敛/恶化榜；缺省 = 最新周最后一条 vs 上一周最后一条。返回每规则 `{rule_id,title,level,from_count,to_count,delta,exempt_count}`，按 \|delta\| 降序 |
| `GET /api/audit/runs`（扩展） | 列表补 `exempt_count` / `exceptions_hash`（历史列表要显示例外数与指纹变化） |

统计口径：**建议数 = 未豁免的 findings**（`exempt_by IS NULL` 或 `exempt_json.status = 'expired'`）；
**例外数 = 生效中 + 即将到期**。站点过滤经 `device_name` 关联 `devices.location`（findings 里冗余了设备名，改名/删设备时退化为"无站点"，不算错）。

**3. 采集后自动跑（去抖）**

采集是**前端 worker 队列逐台调单设备端点**（`POST /api/collect/{device}`），没有服务端批次概念。
所以在后端做去抖：每台采集成功后调用 `schedule_post_collect_audit()` ——
重置一个延迟定时器（默认 60 秒），批次静默后跑一轮（`trigger=post_collect`）。
好处：UI 批量与 CLI 采集都能覆盖；一批只跑一轮且数据完整。

- 开关：`config/settings.yaml` → `audit: {run_after_collect: true, post_collect_delay: 60}`（**默认开**，用户定案）
- **失败绝不影响采集**：整段包 try/except，只打印日志
- 定时器为 daemon 线程；服务重启丢失无所谓（下一批会重新触发）

## 四、验证方式

- 单测：周聚合（同周多条取最后一条、本周无数据不出现）、站点过滤、建议数/例外数口径、
  diff 计算（豁免不计入命中数）、去抖（连续调用只跑一次）、开关关闭不跑、审计抛错不影响采集
- 回归：387 项全绿；移植等价性 486=486
- 端到端：浏览器打开「配置审计」→ 手工触发一轮 → 历史列表出现新记录 →
  趋势图/榜渲染（数据不足时给出可读提示）→ 明细下钻可按档位/设备筛选

## 五、风险与坑

1. **提取 `run_full_audit()` 是重构既有代码**：端点行为必须逐字段不变（含返回结构与错误路径）。
2. **周归属用 ISO 周**（`isocalendar()`），与库内 `week` 列（`YYYY-WW`）格式一致；跨年周（2026-W53 → 2027-W01）要测。
3. **`json_extract` 依赖 SQLite JSON1**：Python 3.14 自带的 SQLite 已内置；测试里会实际跑一遍（不用 mock）。
4. **定时器测试**：用 `post_collect_delay=0` + 立即等待，避免测试里睡 60 秒；并断言"连续采集只跑一轮"。
5. **历史数据**：现有库里可能只有很少几次运行（当前 1 次），图表要有"数据不足"的可读状态，
   不能因为只有一个点就画一条看不出趋势的线而不给解释。
6. **榜单基准缺数据**：上一周没有运行时不渲染榜，提示"需要至少两周的数据对比"。
